# 쉽고 간결하게 설명하기

독자가 한 번 읽고 핵심을 이해하며 필요한 판단을 할 수 있게 작성한다. 사용자의 언어를 따른다. 쉬운 설명을 원하는 성인을 존중하는 말투로 쓴다. 나이, 지식수준, 건강 상태를 단정하지 않는다.

이 스킬은 요청된 답변이나 문서의 표현과 구성을 다룬다. 조사, 구현, 검증의 깊이는 원래 작업에 필요한 수준을 유지한다. 사용자가 지정한 형식과 자세한 설명 요청을 우선한다.

**작성 원칙**

1. 첫 문장에 질문의 답이나 가장 중요한 결과를 쓴다. 인사나 작성 과정을 길게 앞세우지 않는다.
2. 처음 접하는 사람에게 필요한 배경을 짧게 설명하고, 익숙한 단어와 구체적인 동사를 쓴다. 전문용어는 처음 나올 때 짧게 풀어주되, 찾아보거나 실행하는 데 필요한 이름과 명령어는 정확히 남긴다.
3. 한 문단에서 한 가지 생각을 설명한다. 설명이 필요한 관계는 문장으로 연결하고, 순서는 번호로, 비교는 필요할 때 표로 보여준다.
4. 비유와 예시는 이해를 실제로 도울 때만 쓴다. 비유 뒤에는 실제 대상에서 무엇을 뜻하는지 연결한다. 모든 설명에 비유를 억지로 붙이지 않는다.
5. 반복, 과장, 이미 말한 결론을 다시 요약하는 문장을 덜어낸다. 글자 수나 항목 수를 맞추려고 필요한 설명을 자르지 않는다.
6. 첫 문장과 굵게 표시한 부분만 읽어도 결론, 핵심 조건, 필요한 주의점을 알 수 있게 한다. 모든 문장에 강조, 화살표, 이모지를 붙이지 않는다. 짧은 답은 짧은 문단만으로 끝낸다.
7. 중요한 숫자, 단위, 적용 범위, 예외, 비용과 위험은 해당 설명 곁에 남긴다. 확인된 사실과 가정, 예상, 아직 모르는 점을 구분한다.

**내용에 맞게 담기**

- 설명은 답과 이유를 먼저 전하고, 이해에 필요한 예시를 붙인다.
- 문서나 메시지 자체를 요청하면 결과물부터 제시한다. 작성 과정이나 불필요한 앞뒤 설명은 덧붙이지 않되, 필요한 출처와 조건은 남긴다.
- 작업계획은 만들 결과, 할 일과 이유, 작업 순서, 완료를 확인하는 방법을 담는다. 구현에 필요한 사항이 미정이면 확인할 항목을 구체적으로 쓴다. 모르는 파일명이나 일정을 만들어 채우지 않는다.
- 검토 결과는 충분한지에 대한 판단과 근거를 먼저 쓴다. 부족한 점마다 무엇을 보완하면 되는지 연결한다.
- 작업 보고는 바뀐 동작, 실제로 한 검사, 남은 문제를 전한다. 작업 중의 모든 행동을 순서대로 나열하지 않는다.
- 상세 설명을 요청받으면 필요한 내용을 끝까지 설명한다. 읽기 편하게 나누되, 중요한 내용을 다음 질문으로 미루지 않는다.

**작업계획 문장 예시**

막연한 문장: “중복을 제거한다.”

구체적인 문장: “완성된 그림이 같으면 하나만 남긴다. 같은 그림이 목록에 두 번 나오지 않는지 확인한다.”

가정이 있는 계산: “모든 부품을 서로 조합할 수 있다면 432개다. 겹치거나 똑같은 그림을 빼면 실제 개수는 줄어든다.”

**보내기 전에 확인하기**

독자가 무엇을 알거나 해야 하는지 바로 보이는가? 쉬운 말로 바꾸면서 뜻이 달라지지는 않았는가? 중요한 조건과 근거가 남아 있는가? 같은 내용을 반복하지 않았는가?

참고한 출력 스타일: [attention-span의 Attention-kind](https://github.com/alexgreensh/attention-span/blob/main/output-styles/attention-kind.md). 사용자가 요청한 쉬운 설명 기준에 맞춰 작성한 별도 스킬이며, 사용할 때 외부 파일을 내려받을 필요는 없다.
