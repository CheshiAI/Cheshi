# 앱 업데이트

Cheshi는 [CheshiAI/Cheshi의 공개 릴리스](https://github.com/CheshiAI/Cheshi/releases)를
앱 시작 시 한 번, 실행 중에는 매시간 확인합니다. 앱 시작은 네트워크 응답을 기다리지
않습니다. 잠자기에서 깨어났을 때 마지막 확인 시도로부터 한 시간이 지났다면 다시
확인합니다. 오프라인 상태나 요청 실패는 작업을 중단하거나 이미 발견한 업데이트를
제거하지 않습니다.

설치 가능한 새 릴리스를 발견하면 워크스페이스 상태 표시줄과 프로젝트 선택 화면에
**종 아이콘 / Update available** 표시가 나타납니다. 이를 선택하면 설치된 버전과
새 버전, 일반 텍스트 형식의 릴리스 노트 요약, **View full release**를 볼 수 있습니다.
**Cancel**은 대화상자만 닫고 업데이트 표시는 유지합니다. **Update**는 패키지를
다운로드하고 검증한 뒤 워크스페이스 복원을 준비하고 앱을 재시작합니다.
설치 시도가 실패하면 다시 시도할 수 있습니다.

## 로컬에서 업데이트 UI 미리보기

현재 개발 앱을 종료한 뒤 다음 명령을 실행합니다.

```sh
bun run desktop:dev:update-preview
```

이 명령은 개발 세션에 `CHESHI_UPDATE_PREVIEW=1`을 설정합니다. 상태 표시줄과
프로젝트 선택 화면에 영문 예제 릴리스 노트가 포함된 가상의 `v0.0.2-alpha`
업데이트가 표시됩니다. **Update available**을 누르면 대화상자가 열립니다.
**Cancel**을 누르면 업데이트 표시를 유지한 채 닫힙니다. **Update**는 다운로드와
설치 진행 상황을 모의 실행한 뒤, 재시도 UI를 확인할 수 있도록 의도적인 오류를
표시합니다. 실제로 공개된 릴리스가 아니므로 **View full release**는 비활성화됩니다.

미리보기는 업데이트 확인 요청, 다운로드, 설치 변경, 워크스페이스 체크포인트 저장,
재시작을 수행하지 않습니다. 릴리스도 공개하지 않습니다. 일반적인 앱 시작 과정은
그대로 실행됩니다. 패키징된 앱에서는 이 플래그를 무시합니다. 실제 업데이트 확인으로
돌아가려면 `bun run desktop:dev`로 다시 실행합니다. 셸에서 `CHESHI_UPDATE_PREVIEW`를
내보낸 상태라면 먼저 해당 환경 변수를 해제합니다.

## 버전과 릴리스 채널

- 내부 테스트에는 `v0.0.1-alpha`, `v0.0.2-alpha` 등의 버전을 사용합니다.
- 공개 Homebrew 배포는 별도로 `v0.0.1-preview`부터 시작하고,
  `v0.0.2-preview`와 후속 preview 버전으로 이어집니다.
- Preview 설치본은 더 최신인 preview와 정식 릴리스를 확인하며 alpha 릴리스는
  제외합니다. 정식 설치본은 정식 릴리스만 확인합니다. 내부 테스트용 alpha 빌드는
  더 최신인 alpha, preview, 정식 릴리스를 모두 확인할 수 있습니다.
- 모든 버전 비교는 SemVer 우선순위를 따릅니다. 번호가 더 높은 alpha에서
  `v0.0.1-preview`로 내려가는 특별한 다운그레이드 처리는 없습니다.
  공개 preview 배포를 시작할 때 내부 빌드는 수동으로 교체합니다.
- 초안 릴리스는 무시합니다. 지원하는 사전 릴리스 태그도 릴리스 목록 조회에
  포함하므로 GitHub의 **Pre-release** 설정이 alpha나 preview 업데이트를 숨기지
  않습니다. 릴리스 노트는 원래 언어를 유지합니다.

## 설치 가능한 릴리스 준비

빌드 전에 앱 버전을 설정하고 일치하는 GitHub 태그를 사용합니다. 예를 들어 앱 버전이
`0.0.2-alpha`라면 태그는 `v0.0.2-alpha`입니다. 지원하는 아키텍처별로 서명된 macOS
앱을 포함하는 ZIP 파일을 첨부합니다. 업데이터는 다음 두 가지 자산 이름을 지원하며,
버전과 아키텍처 부분은 실제 값으로 바꿉니다.

- `Cheshi-0.0.2-alpha-darwin-arm64.zip`
- `Cheshi-darwin-arm64-0.0.2-alpha.zip`

버전은 `.env.product`의 `APP_VERSION`에서 가져옵니다. 배포 빌드마다
`APP_BUILD_NUMBER`도 올립니다. Forge는 루트 `package.json`의 개발용 버전과 별개로
이 버전을 앱과 ZIP 파일 이름에 동일하게 사용합니다.

`bun run desktop:make:signed`로 서명 및 공증된 macOS ZIP을 빌드합니다.
이 명령은 Git에서 제외된 `.env.signing` 파일을 읽고 Forge에
`CHESHI_SIGN_RELEASE=1`을 설정합니다. 다음 변수를 해당 로컬 파일에 설정하거나
빌드 환경을 통해 제공합니다.

```dotenv
MACOS_SIGNING_IDENTITY="Developer ID Application: Your Company (YOURTEAMID)"
MACOS_NOTARY_PROFILE="YourNotaryProfile"
```

서명 ID에는 회사 이름과 Team ID가 포함됩니다. `.env.signing`은 Git과 패키징된
앱에서 제외됩니다. 서명 빌드에는 두 값이 모두 필요합니다. 누락된 값이 있으면
다른 ID나 프로필로 대체하지 않고 설정 단계에서 실패합니다. 빌드하는 컴퓨터에는
개인 키를 포함한 인증서와 검증된 공증 프로필이 있어야 합니다. 인증 정보는 macOS
키체인에 보관하며, 암호나 개인 키를 저장소에 추가하지 않습니다.
서명이나 공증에 실패하면 빌드도 실패합니다.

서명하는 macOS 빌드는 Forge 서명 전에 새로 컴파일한 Bun 실행 파일을 정규화합니다.
일부 Bun 버전은 Mach-O 코드 서명 뒤에 컴파일러 템플릿의 잔여 바이트를 남겨
`main executable failed strict validation` 오류를 일으킵니다. 빌드는 선언된
바이너리 범위를 검증한 뒤 사용하지 않는 끝부분을 제거하며, 서명 검증을 생략하지
않습니다. Forge는 첫 서명 오류에서 중단하고 서명되지 않은 앱의 공증을 시도하지
않습니다. 컴파일러가 남기는 오래된 서명 끝부분과 마지막 페이지 해시 문제는
[Bun 서명 결함 분석](https://github.com/oven-sh/bun/pull/32162)을 참고하세요.
Forge는 컴파일러의 임시 서명을 검증된 Developer ID 서명으로 교체합니다.

일반 `desktop:make`와 `desktop:package` 명령은 `CHESHI_SIGN_RELEASE=1`을 명시적으로
설정하지 않는 한 서명이나 공증을 요청하지 않습니다. 서명 빌드 명령은 현재 컴퓨터의
아키텍처와 설정된 앱 버전을 사용합니다. 버전을 변경하거나 릴리스를 공개하거나
GitHub에 업로드하지 않습니다. 공증 과정에서는 패키징된 앱을 Apple에 업로드합니다.
공개 배포 전에 생성된 앱의 서명, 공증 티켓, 신규 설치, 서명된 빌드 간 실제
업데이트를 검증합니다.

Intel macOS 빌드에는 `arm64` 대신 `x64`를 사용합니다. 자산은 CheshiAI/Cheshi의
해당 릴리스에 속해야 하며, 크기가 0보다 커야 합니다. GitHub 자산의 `digest`에는
`sha256:`과 SHA-256 해시가 포함돼야 합니다. Electron이 설치를 준비하기 전에
다운로드한 파일의 크기와 해시를 기록된 값과 비교합니다.

현재 자동 설치에는 유효한 Developer ID Application 서명이 있는 패키징된 macOS
앱이 필요합니다. 앱은 마운트된 이미지나 App Translocation 위치가 아닌, 쓰기 가능한
설치 위치에서 실행돼야 합니다. 교체할 앱도 Electron의 서명된 업데이트 요건을
충족해야 합니다. 개발 실행에서는 업데이트 알림을 표시할 수 있지만 설치할 수는
없습니다. 지원하지 않는 플랫폼이거나 검증된 일치 ZIP이 없는 릴리스는 설치를
비활성화하고 이유를 함께 표시합니다.

## 워크스페이스 복원

재시작 전에 Cheshi는 저장하지 않은 에디터 내용을 포함한 워크스페이스 복원 상태를
저장합니다. 진행 중인 채팅 작업이나 비어 있지 않은 채팅 초안이 있으면 사용자가
작업을 마치거나 초안을 지울 때까지 설치를 차단합니다. 워크스페이스를 복원해도
실행 중이던 터미널 명령은 다시 시작하지 않습니다. 해당 프로세스는 앱 종료 시
중단되며, 필요하면 수동으로 다시 실행해야 합니다.

이 기능을 추가하는 것만으로 GitHub 릴리스를 공개하거나 설치 파일을 업로드하지는
않습니다. 전체 설치 흐름을 검증하려면 별도로 공개한 서명된 릴리스와 패키징된
이전 버전 앱이 필요합니다.
